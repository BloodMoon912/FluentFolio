# AGENTS.md

Astro 7 SSR site (`output: 'server'`, `@astrojs/cloudflare` adapter) deployed to Cloudflare Workers with D1. Production deploys via Cloudflare's native Workers Builds connected to GitHub `main`.

## Commands

- `npm run dev` — `astro dev` (local SSR). Local worker secrets go in `.dev.vars` (git-ignored), not `.env`.
- `npm run check` — `astro check`. Type-checks `src/`, `tests/` and the processed `<script>` blocks.
- `npm run lint` — `scripts/lint-markdown.mjs`, a small high-signal markdownlint rule set over this repo's own documentation.
- `npm run validate:md` — `scripts/validate-markdown.mjs`. Content-level validation of `src/content/**`: frontmatter fields/types/dates, image paths (public/relative), internal links and draft links, `relatedLore`/`relatedWords`/`relatedEntries` integrity, undefined `[[word]]` tokens and empty bodies. `--strict` promotes warnings to errors. CI runs it after `lint`.
- `npm run format` / `npm run format:check` — Prettier over the repository. `.prettierignore` deliberately excludes the imported Fluent design spec (now under `docs/`), `src/content/` (published posts are authored through the CMS, not by tooling) and `tests/fixtures/` (byte-for-byte copies used by the seed script).
- `npm test` — `node --test "tests/*.test.ts"`. Pure-function tests only, importing the TypeScript sources directly, so it needs **Node >= 22.18**; the repository itself runs on **22.23.4** (see `.nvmrc`).
- **Use Node 22.23.4 exactly (or a newer 22.x).** Astro 7.4.2 requires `>=22.23.4`; `.nvmrc`, `engines.node` and CI's `node-version` are all pinned. Cloudflare Workers Builds reads `.nvmrc` (or set `NODE_VERSION=22.23.4` in the build environment; its default is Node 24.21). Node 24 still fails `astro check`/`build` locally with the Vite module-runner `require is not defined` error, followed by a libuv assertion on Windows. It is a toolchain incompatibility, not a repository defect. Do not "fix" it by editing `src/content.config.ts` or by pinning a different Vite. In a sandboxed shell, `npm test` also needs `node --test --experimental-test-isolation=none "tests/*.test.ts"`, because Node's default per-file isolation is denied there as `spawn EPERM`.
- `npm run build` — production build. Use it to verify any change. `prebuild` runs `scripts/fetch-content.mjs`, which is a no-op while `src/content` has Markdown and, in the optional private-content mode, clones the private content repository into it. `npm run fetch:content -- --from ../fluentfolio-content` mirrors a local clone for dev. On Workers Builds a failed fetch fails the build on purpose; see `docs/PRIVATE-CONTENT-REPO.md`.
- `npm run check:og-png` — `scripts/check-og-png.mjs`. Post-build assertion that `/og.png` and every published article `/og/<id>.png` is a real 1200×630 PNG (magic bytes + IHDR) and that no card is missing. Run it after `npm run build`; it is not part of `npm test`.
- `npm run preview` — `astro preview` (server-renders the built output locally).
- `npm run deploy` — build + `wrangler deploy`. Manual local deploys only; `main` auto-deploys via Workers Builds.
- `npm run cf-typegen` — `wrangler types`. Not wired into compilation; `Env` is hand-declared in `src/env.d.ts` (see gotcha below).

## Type checking

`npm run check` is green and must stay green: CI runs it first, so a red `astro check` fails before lint, tests or the build are reached.

Two hand-written ambient files make that possible, because nothing installs `@cloudflare/workers-types` and `npm run cf-typegen` is deliberately not wired into compilation:

- `src/cloudflare-runtime.d.ts` declares the `cloudflare:workers` module, the `D1Database` and `R2Bucket` shapes this project uses, and the Workers-only `RequestInit.cf` / `Request.cf` extensions. **Keep it in sync whenever a binding, a query shape or a fetch option changes** — before it existed, those unresolved names produced 18 of the 65 type errors and made a real error impossible to spot.
- `src/page-globals.d.ts` declares the `window` members shared between the shell script and the page scripts (`T`, `getLang`, `setLang`, `__bmHomeCleanup`, and the visit flags).

`public/` stays excluded from the main `tsconfig.json` program: those files are copied verbatim into `dist/` and never bundled, so they are not part of the Astro/TS module graph. They are type-checked separately by `npm run check:public` (`tsconfig.public.json`, `allowJs` + `checkJs` + `strict`), which CI runs right after `npm run check`. That program includes `src/page-globals.d.ts` and `types/public-scripts.d.ts` for the `window` APIs and Turnstile types; annotate the browser scripts with JSDoc rather than adding imports, because they must stay dependency-free at runtime.

Inline `is:inline` scripts are emitted verbatim and therefore **cannot use TypeScript syntax — only JSDoc** (`/** @type {…} */`). The remaining `is:inline` tags in pages are plain `src="…"` loaders, so new browser logic belongs in `public/scripts/*.js` where `npm run check:public` covers it.

## Deploy & production

- Production deploys are driven by Cloudflare Workers Builds (build `npm run build`, deploy `npx wrangler deploy`) on every push to `main`. `.github/workflows/ci.yml` only validates — **do not add a GitHub Actions deploy step** (two deploy systems conflict).
- CI runs, in order: `npm ci`, `npm run check`, `npm run lint`, `npm run validate:md`, `npm run format:check`, `npm test`, `npm run build`. No secrets, no Wrangler, no schedule.
- **Regenerate `package-lock.json` with npm 10, not npm 11.** Workers Builds runs `npm ci` on Node 22.x, and a lockfile written by npm 11 is rejected as out of sync — it omits optional entries such as `@emnapi/core` and `@emnapi/runtime` that npm 10 expects. The repository is currently developed on Node **22.23.4** / npm **10.9.9**, which produces the same lockfile format. On a machine with npm 11:

  ```bash
  npx --yes npm@10.9.2 install --package-lock-only
  npx --yes npm@10.9.2 ci --dry-run
  ```

  A lockfile that fails the second command fails the whole deploy, and it fails _after_ the build environment is provisioned, so the log looks like an infrastructure problem rather than a dependency problem.

- **`package.json` carries an `overrides` block, and it must be kept valid.** Critical/high advisories are at **0** as of 2026-10-25 (Astro `7.4.2`; `dompurify` `3.4.17`; `typescript` pinned `6.0.3`; `wrangler` `4.152.0`; `vite` `8.3.5`; `zod` `4.6.7`; `undici@7` `7.30.1` / `undici@8` `8.12.3`; `source-map-js` `1.2.2`). `npm audit` still reports ~22 low/moderate advisories from build-only tooling (`@swup/astro` → microbundle/postcss, `markdownlint` → katex) with no in-range fix; see `docs/upgrade-audit.md` §6/§9.4. Rules: (1) never run `npm audit fix --force` — its "fix" downgrades `@swup/astro` to 0.2 and breaks the site's page transitions; (2) after changing any override, regenerate the lockfile with npm 10 and run the full chain, since a pin that breaks a build tool fails at `npm run build`, not at install; (3) `serialize-javascript` is pinned to 7.x although its parent resolves 4.x — there is no patched 4.x. If `@swup/astro` is bumped, re-check that pin and re-run `npm audit` rather than trusting it.

- Secrets are set with `npx wrangler secret put` (`STEAM_API_KEY`, `STEAM_ID`, `VISITOR_SALT`, `VISITOR_COOKIE_SECRET`, `TURNSTILE_SECRET`, `DISCORD_USER_ID`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `GITHUB_TOKEN`, `DISCORD_BLOG_WEBHOOK_URL`) or in the dashboard. Never commit their values; `.dev.vars` and `.env*` are git-ignored. `.env.example` lists every one. `ADMIN_SESSION_SECRET` is now mandatory for any admin login (password or Passkey); `ADMIN_PASSWORD` is only the optional password fallback.
- Admin edge auth is configured with **plain vars in `wrangler.jsonc`**, not secrets: `ACCESS_TEAM_DOMAIN`, plus either one shared `ACCESS_AUD` or both `ACCESS_ADMIN_AUD` + `ACCESS_API_AUD`; and `ADMIN_WEBAUTHN_RP_ID` / `ADMIN_WEBAUTHN_ORIGIN` for the canonical production origin. Leaving the Access vars empty fails closed (every `/admin*` and `/api/admin*` request returns 503) — that is intentional. Passkey storage requires applying `migrations/0006_admin_passkeys.sql` before deploying the code that uses it.
- `GITHUB_REPO` is the repository the CMS commits to (this one by default, the private content repository in the optional private-content mode) and `GITHUB_TOKEN` is scoped to it only. Build-time `CONTENT_REPO_TOKEN` (read-only), `CONTENT_REPO` and `CONTENT_REQUIRED` are Workers Builds build variables, not Worker secrets.
- The CMS additionally needs the plain vars `GITHUB_REPO`, `GITHUB_BRANCH` and `R2_PUBLIC_BASE_URL`, plus the `BLOG_IMAGES` R2 binding. Without `GITHUB_TOKEN` / `GITHUB_REPO`, `/api/admin/*` returns 503.
- D1 binding `DB`, config in `wrangler.jsonc`, migrations in `migrations/` (numbered `.sql` files). New schema change = new file, then apply locally (`npx wrangler d1 migrations apply personal-site --local`) and — as an explicit pre-deploy step — remotely (`--remote`). Code that reads new columns/tables must deploy after the remote migration (SQLite `ALTER TABLE`), and must degrade when the migration has not been applied yet. Current schema: `0001` init (`visits`, `activity`, `incidents`), `0002` activity, `0003` visitor geo/referrer, `0004` site start time, `0005` CMS drafts, `0006` admin passkeys, `0007` visitor indexes, `0008` admin sessions, `0009` status checks. Next number: `0010`.
- Rate limiting bindings live in `wrangler.jsonc`: `ADMIN_LOGIN_RATE_LIMIT` (5 login attempts/IP/minute, every attempt counts), `ADMIN_PASSKEY_RATE_LIMIT` (20 passkey ceremonies/IP/minute) and `VISITOR_RATE_LIMIT` (60 visitor beacons/IP/minute). Keep `src/env.d.ts` in sync.
- `src/env.d.ts` declares `Env` manually. Keep it in sync when adding bindings.

## Admin authentication (double layer)

`/admin`, `/admin/login` and every `/api/admin/*` route pass **two independent gates**:

1. **Cloudflare Access** at the edge, plus a mandatory Worker-side JWT check in `src/middleware.ts` → `src/lib/cloudflare-access.ts` → `src/lib/cloudflare-access-core.ts`. The Worker verifies the RS256 signature against the team JWKS, the exact issuer, the Access Application AUD and the `exp`/`nbf`/`iat` claims; it does not trust the bare presence of `Cf-Access-Jwt-Assertion`. `/admin*` and `/api/admin*` are separate route families, so either configure one shared `ACCESS_AUD` or both `ACCESS_ADMIN_AUD` + `ACCESS_API_AUD` (partial split config fails closed). Missing/invalid config → 503; missing/invalid token → 403. The only bypass is `astro dev` on `localhost`/`127.0.0.1`/`::1`.
2. **The site's own account session** (`src/lib/admin-auth.ts`): Passkey first (`src/lib/admin-passkeys.ts`, `@simplewebauthn/server` 14.0.3, D1 tables from `migrations/0006_admin_passkeys.sql`) with `ADMIN_PASSWORD` as the fallback for `POST /api/admin/login`. The session cookie is `__Host-bm-admin` (HttpOnly, Secure, SameSite=Lax, 7 days): a random session id plus an HMAC signed with the dedicated `ADMIN_SESSION_SECRET`, and every check also reads the `admin_sessions` row (`migrations/0008_admin_sessions.sql`) so a session can be revoked before expiry. D1 is part of authentication now — a missing binding, a query error or a not-yet-applied `0008` returns **503**, never a silent allow or an ordinary 401. `POST /api/admin/logout` revokes the current session and clears the cookie; `POST /api/admin/logout-all` revokes every active session (admin UI has a 登出所有裝置 button). Visitor cookies are scoped differently and can never validate as an admin session. Passkey challenges live in D1 for 5 minutes and are consumed atomically with `DELETE … RETURNING`, so a challenge can never be replayed. Registration requires an existing admin session.

`requireAdmin()` (used by every mutating admin route) also rejects state-changing requests whose `Origin` does not exactly match the request origin, as a second CSRF barrier alongside SameSite. `ADMIN_LOGIN_RATE_LIMIT` is consulted **before** the password comparison and every attempt (success or failure) consumes the bucket; over the limit the route returns 429 + `Retry-After` without comparing the password. The CMS browser API is **GET for reads and POST for every mutation** (create/save/publish/delete/batch/taxonomy), with JSON bodies — see `docs/CMS-HTTP-CONTRACT.md`; GitHub REST calls made server-to-server still use GitHub's own PUT/DELETE verbs. Login JSON bodies are capped at 8 KB and passkey ceremony bodies at 64 KB, enforced by counting the actual bytes streamed.

## Security headers & CSP

`src/middleware.ts` sets `x-content-type-options`, `referrer-policy`, `x-frame-options`, `permissions-policy` and an enforced baseline `content-security-policy: frame-ancestors 'self'; object-src 'none'; base-uri 'self'` on every Worker response. It also emits a **`Content-Security-Policy-Report-Only`** header for SSR HTML only. The candidate policy is **nonce-free**: every executable script is a same-origin file under `/scripts/` (or Astro's hashed `/_astro/`), so `script-src` is `'self' https://challenges.cloudflare.com` (Turnstile). Do not put executable inline `<script>` back into a page; `npm run check:inline-scripts` fails the build if one reaches `dist/`.

The Report-Only policy is **observational**: never flip it to enforced, and never switch to Astro's built-in `security.csp` (enforcing `<meta>` CSP, no Report-Only mode), before the limitations documented in `DEPLOY-CLOUDFLARE.md` are solved — prerendered pages are static assets that never pass through middleware, so they do not receive the Report-Only header even though their scripts are all same-origin now. Because prerendered pages skip middleware, `public/_headers` repeats the non-CSP security headers plus the same enforced CSP baseline for static assets; that file is the only place those pages can get them. HSTS is set in the Cloudflare dashboard, not in code. `R2_PUBLIC_BASE_URL`'s origin is added to `img-src` automatically; add any new third-party image/connect origin to `src/lib/csp-core.ts` and its tests.

## Visitor statistics & Turnstile

`POST /api/visitors` records page views; Turnstile gates that endpoint and nothing else, with `action: 'visit'`. Protection is **fail-open by configuration**: with no `TURNSTILE_SECRET` on the Worker the endpoint behaves exactly as it would without Turnstile. Never make that secret mandatory in code — a missing secret must not become a site-wide analytics outage.

An earlier integration of this widget looped (a visitor solved a challenge and another appeared immediately) and was removed. Both causes are now fixed and must stay fixed: **Read this before touching either half.**

- **Beacon client** (`public/scripts/visit-beacon.js`, included from `BaseLayout.astro` with `data-swup-ignore-script`): sends `POST /api/visitors` on first load and on every `swup:page:view`; a path is sent at most once per tab (in-memory `Set`, no storage); `/admin`, `/api` and `/og` prefixes are never beaconed. The first beacon of a tab includes `document.referrer`; later SPA navigations do not. The visit/Turnstile code used to live in `home-dashboard.js` and must not move back there — the homepage is now prerendered and the beacon has to run on every page.
- **Cookie semantics**: `__Host-bm-visit` (30 days) marks a _returning browser_ and suppresses Turnstile, but it **no longer suppresses recording** — every accepted beacon is a view. Without a valid cookie and only when `TURNSTILE_SECRET` is set, the server answers `403` with `reason: 'missing-token'`; that is the only reason a client may act on.
- **Challenge client** (`public/scripts/turnstile-client.js`): no `reset()` export and no retry loop. The widget is removed the instant it produces a token; `refresh-expired: 'never'`, `refresh-timeout: 'manual'` and `retry: 'never'` disable Turnstile's own re-arming; `expired-callback` fails instead of re-arming; at most one widget exists per page no matter how often the calling script re-runs under Swup. The beacon asks for a token at most once per tab (`window.__bmVisitChallengeAttempted` is set _before_ the attempt) and never retries on `hostname-mismatch`/`action-mismatch` — those are configuration bugs.
- **Server** (`src/pages/api/visitors.ts`, pure rules in `src/lib/visitor-core.ts`): the path must start with `/`, be ≤200 chars after stripping query/hash, contain only legal URL path characters, avoid dot segments and match a known route prefix (`/`, `/posts`, `/posts/blog/`, `/posts/novel/`, `/dictionary`, `/world`, `/status`, `/about`, `/privacy`, `/terms`); invalid input returns `{ ok: true, recorded: false }` without a write. Per-IP `VISITOR_RATE_LIMIT` returns 429. The same `visitor_hash` + path written within 30 seconds counts once. The referrer host comes from the beacon body's `document.referrer` — **never** the `Referer` header (a same-origin fetch would just send this site's own URL). The IP is combined with `VISITOR_SALT` and hashed; the raw IP is never stored.
- **Retention/aggregation**: aggregate queries cover 30 days and the overview cards 180 days (`VISIT_OVERVIEW_DAYS`); rows older than `VISIT_RETENTION_DAYS = 180` are deleted opportunistically after a successful write (about 1% of writes, at most once per isolate per UTC day) and never on a GET. `GET /api/visitors` is edge-cached for 60 s with a cookie-free key; the cookie-derived `visited` field is merged after the cache read.
- Turnstile verification (`src/lib/turnstile.ts`) follows Cloudflare's canonical contract — `success`, the expected `action`, and a `hostname` on the `TURNSTILE_HOSTNAMES` allow-list are all required — but reports _which_ check failed instead of a bare boolean, and `POST /api/visitors` logs that reason. An empty `TURNSTILE_HOSTNAMES` is a hard failure, not a silent pass. Production must list only the real hostnames; `localhost` and `127.0.0.1` belong in `.dev.vars`.

## Activity feature

The homepage Discord presence panel proxies **Lanyard live** (`GET /api/activity`, driven by `env.DISCORD_USER_ID`, with a browser WebSocket fallback). `POST /api/activity` is disabled (returns 405); the old `scripts/update-activity.mjs` / `npm run activity` / `ACTIVITY_*` env-var flow was removed, including the never-read `ACTIVITY_TOKEN`.

`/api/activity` (10 s), `/api/status` (30 s) and `/api/visitors` aggregates (60 s) are edge-cached through `src/lib/cached-json.ts`: the cache key is origin+pathname only (no cookies/query), the **stored copy** uses `Cache-Control: public, max-age=<ttl>` so the Workers cache can actually reuse it, and responses carry `x-cache: HIT|MISS` for diagnosis. Producers must stay request-independent; per-request fields are applied in `decorate` after the cache read — that is how `/api/visitors`'s cookie-derived `visited` and `/api/status`'s `system.edge` (the requester's `request.cf` city/region/ISP, which must never leak to another visitor in the same colo) avoid being cached. Do not move them into the producer. Because a decorated response contains per-visitor data, it is returned as `Cache-Control: private, max-age=0` (no shared cache may store it); only undecorated responses such as `/api/activity` keep `public, max-age=0, s-maxage=<ttl>`.

`/api/status` reports only real probes: `website` = this request's handling time, `database` = a timed D1 `SELECT 1`, `activity` = Lanyard, `steam` = Steam Web API. Do not add an `ok: true` row without a probe behind it. Results are sampled into `status_checks` (at most once per 5 minutes, written via `waitUntil` after the response) and `/status` renders the last 24 hours; there is no Cron Trigger.

D1 tables: `visits`, `cms_drafts`, `admin_passkeys`, `admin_webauthn_challenges`, `admin_sessions` and `status_checks` are active; `incidents` is a legacy unused table (kept, not reused); `activity` is read only by `about.astro` for the site start time (`SELECT started_at FROM activity WHERE id = 1`).

## Local CMS

There is no local desktop CMS. The former `scripts/cms/` Node tool was the predecessor of the online admin CMS; it lived in git history and has now been removed from the repository and from `package.json`. Do not reintroduce references to it. The CMS manages all four collections through `src/pages/api/admin/content*`; `src/lib/frontmatter.ts` is the single source of truth for serialised frontmatter (blog keeps the original serializer, other collections use `serializeContentFrontmatter`). Browser-facing admin calls are GET for reads and POST for every mutation, and batch taxonomy edits must update the D1 draft copy of each affected item (otherwise a stale draft silently reintroduces the old category/tag on the next load); `posts/batch.ts` and `posts/index.ts` are the legacy blog-only endpoints and follow the same draft rules.

## Content & UI conventions

- **Four content collections**, all defined in `src/content.config.ts`: `blog` (essays; frontmatter `title`, `date`, `description` required, plus `type` defaulting to `essay`), `novel` (`title`, `volume`, `chapter`, `date`, `order`, `relatedLore`), `dictionary` (`word`, `ipa`, `partOfSpeech`, `definition`, `etymology`, `relatedWords`) and `world` (`title`, `type`, `description`, `relatedEntries`). `date` replaced the old `pubDate`; `src/lib/frontmatter.ts` still reads `pubDate` as a fallback for old drafts but only writes `date`. Do not add content to `src/lib/data.ts`.
- **Routes**: `/posts` is the tabbed index (`?tab=blog|novel`); articles live at `/posts/blog/[slug]`, chapters at `/posts/novel/[slug]`, and both are **prerendered** (`getStaticPaths` over the published ids). Their parent `/posts/blog` and `/posts/novel` are not routes — link to `/posts?tab=blog` / `/posts?tab=novel` instead. `/dictionary` and `/world` list pages are SSR; their `[slug]` detail pages are prerendered. `/blog*` routes no longer exist (404). The homepage, `/privacy`, `/terms` and `/404` are **prerendered** (their content is baked at build time and the live panels fetch `/api/*` client-side); `/posts`, `/about` and `/status` stay SSR — `/posts` because `?tab=` is server-rendered state, `/about` because it reads D1, `/status` because it probes per request. The homepage merges both content streams through `buildMixedFeed()` in `src/lib/content-feed.ts` — never sort one collection on its own there.
- **Search**: one engine in `src/lib/search-core.ts` (index loading, Fuse config, kind/tag filtering, highlight, `?q=`/`?type=`/`?tag=` helpers) over the prerendered `/search-index.json` (all four collections). Romanisation is precomputed at **build time** in `src/pages/search-index.json.ts` via `pinyin-pro` (Mandarin, tone-less, space-separated + compact + initials) and `to-jyutping` (Cantonese with and without tone, space-separated + compact); drafts never enter the index and blog `tags` stay real tags (category/keywords are separate fields). `SiteSearch.astro` has `topbar`, `menu` and `inline` variants; the whole-site shell search stays available on every route, including `/posts`, `/dictionary` and `/world`, while those index pages additionally render a collection-specific inline variant that filters the server-rendered list in place. The `/posts` tab controller is delegated from the persistent `BaseLayout` script so its click/history handlers survive Swup's `<main>` replacements. `/posts` adds a blog-only tag facet and mirrors `?q=`/`?tag=` into the URL. The admin CMS list uses the same core. Do not reintroduce `CollectionFilter`, `data-search` card attributes or a second search implementation. `public/_headers` caches `/search-index.json` for one hour. Result-kind labels are `search_kind_*` i18n keys — do not hardcode BLOG/NOVEL/…
- **i18n**: the dictionaries and `t()` live in `src/i18n/ui.ts`; `src/lib/i18n.ts` is only a compatibility re-export, so keep new translations in `src/i18n/ui.ts`. Proper nouns come from `src/lib/terminology.ts` (`WORLD_NAME`, `CONLANG_NAME`); do not invent transliterations or alternative names.
- **Word count**: `src/lib/word-count.ts` (`getWordCount`) strips frontmatter, HTML and Markdown syntax, excludes fenced/inline code by default, and counts CJK characters plus Latin tokens. `about.astro` uses it for the site total.
- **`[[word]]` lore links are zero-API**: the Sätteri mdast plugin in `src/lib/lore-plugin.mjs` (wired via `markdown.processor` in `astro.config.mjs`) reads `src/content/dictionary/**/*.md` **at build time** and inlines the definition on the span (`<span class="lore-word" data-lore-word="…" data-tooltip="…" tabindex="0">`). `public/scripts/lore-tooltip.js` only reads `data-tooltip`; there is no `/lore.json` route and no fetch. Undefined words get `data-lore-missing` and no tooltip. The plugin's `node:fs` read must never reach the Worker request path — it is build/dev only.
- **Markdown is sanitized**: every document goes through `satteri-sanitize` as the last `hastPlugins` entry (`src/lib/markdown-sanitize.mjs`). The default allowlist is kept; the only widening is the lore span's `className` / `data-lore-word` / `data-tooltip` / `data-lore-missing` / `tabindex`. Do not add `on*`, `style`, `iframe` or `javascript:` support to make hand-written HTML render; `tests/markdown-sanitize.test.ts` plus `tests/fixtures/security/markdown-xss.md` are the regression gate.
- **Published Markdown is enhanced at runtime** by `public/scripts/markdown-enhance.js` (loaded from `BaseLayout.astro` with `data-swup-ignore-script`): it wraps tables for horizontal scrolling and adds code-block language labels + copy buttons. It must stay idempotent (`data-md-enhanced`, wrapper check) and must not rebind document listeners on Swup `content:replace`/`page:view`. The CMS preview implements the same toolbar/table idea in `src/scripts/admin-cms.ts` with the same class names, and `admin-cms.css` per-collection editor styles (edit/split/preview, focus-writing, lint panel) must keep the `md-*` class names the script actually emits.
- Backlinks are derived, never stored: `src/lib/lore.ts` scans the published `novel` collection for chapters whose `relatedLore` lists a dictionary/world id, and the entry pages render them.
- Reading pages render `<ReadingProgress />` and `<TOC headings={headings} />` (headings come from `render(entry)`); reading typography and the sticky chapter dock live in `src/styles/reading.css`, lore popover styles in `src/styles/lore.css`. Both components bind listeners once and re-measure on every Swup navigation.
- **Mock content is not committed under `src/content/`**: fixtures live in `tests/fixtures/mock-content/`, and `node scripts/seed-mock-content.mjs --seed` copies them in / `--clean` removes only those whitelisted files. Use this for local demos and integration tests.
- **Images**: the adapter uses `imageService: 'compile'` and `<Image />` for `src/assets/background.webp`. Prerendered pages bake the optimised `<Image>` output into their static HTML; the remaining SSR pages (`/posts`, wiki indexes) resolve `<Image />` through the adapter's `/_image` **passthrough**, which streams the already-built file from `ASSETS` (no `IMAGES` binding, no runtime sharp). `public/` still serves the video sources.
- **Open Graph images**: `src/lib/og.ts` builds the card SVG; `/og.svg` and `/og/[slug].svg` are kept for old links, but the default `og:image` is now the PNG `/og.png` (article pages use `/og/<id>.png`). The PNG routes are prerendered and rasterised in the **Node build environment** (`cloudflare({ prerenderEnvironment: 'node' })`) with `@resvg/resvg-js` and the subsetted OFL Noto Sans TC fonts in `src/assets/fonts/` (`loadSystemFonts: false`, explicit `fontFiles`). `public/scripts` is not involved; `src/lib/og-png.ts` is build-only and must never reach the Worker bundle. Run `npm run check:og-png` after a build; new content whose characters are missing from the subset is reported by the card tests/`findUnsupportedCharacters`.
- **Icons are local**: `public/icons/fluent/` contains the vendored Fluent UI SVGs (`@fluentui/svg-icons@1.1.339`, MIT, licence included) used by `FluentIcon.astro`, `BaseLayout`'s theme switcher and the dashboard's activity buttons. `scripts/vendor-fluent-icons.mjs` documents/refreshes them; do not reintroduce a jsDelivr/CDN icon URL. `public/_headers` caches `/icons/*` immutably.
- `docs/` holds the imported Fluent design spec, the upgrade audit, [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), decision records under `docs/DECISIONS/`, and historical process records under `docs/archive/` (marked as possibly outdated — never treat archive content as current truth). Docs-level markdown is still covered by `npm run lint`.
- UI strings and `src/lib/data.ts` (profile, services, socials) are in Cantonese / traditional Chinese (zh-HK); match that tone for new user-facing text. Social icons in `BaseLayout.astro` support keys: `github`, `youtube`, `discord`, `steam`, `x`, `mail`.
- All site timestamps use Hong Kong time (`Asia/Hong_Kong`) via helpers in `src/lib/time.ts` (`formatHKTDate`, etc.). Worker runtime timestamps stay UTC instants and are only formatted in HKT.
- Client-side markup is assembled with template strings and assigned to `innerHTML`, so **every interpolated value from outside this repository must go through `escapeHtml`** (`src/lib/escape-html.ts`; `public/scripts/home-dashboard.js` keeps a verbatim copy because it is served as a plain file and cannot import). A blog title, a Steam name, a visitor referrer host or a linter message interpolated raw is an XSS bug.
- `astro.config.mjs` `site` is the real production origin (`https://www.example.com`); `src/pages/robots.txt.ts` (prerendered from the content collections) and `wrangler.jsonc` `TURNSTILE_HOSTNAMES` reference the same host.
- Swup replaces `<main>` and re-runs the homepage bootstrap on every navigation — `<script is:inline src="/scripts/home-bootstrap.js">` lives inside `<main>`, so `reloadScripts: true` loads it again and the script imports `/scripts/home-dashboard.js`. That re-execution is what re-initialises the dashboard; the bootstrap must stay inside `<main>` (and keep its `src`, with no logic of its own beyond the dynamic import). The dashboard is self-cleaning through `window.__bmHomeCleanup`, which must stop the previous run's timers and WebSocket. Do not turn that bootstrap into a bundled module without replacing the re-initialisation mechanism in the same change.

## Layout

`src/pages/api/*.ts` = worker API endpoints (each imports `env` from `cloudflare:workers` — that is how bindings are accessed, not `locals.runtime`). Pages live in `src/pages`, the public shell in `src/layouts/BaseLayout.astro`, styles in `src/styles/` (built from the `@import` layers in `global.css`), shared server logic in `src/lib/`, UI dictionaries in `src/i18n/`, and tests in `tests/`.

Client code sits in two places, and which one is correct depends on the lifecycle:

- `src/scripts/*.ts` — bundled modules imported by a processed `<script>` in a page. They run once per full page load. `admin-cms.ts` lives here.
- `public/scripts/*.js` — served verbatim at `/scripts/…` and loaded at runtime. `home-dashboard.js` (re-initialised by swup on every navigation), `visit-beacon.js` (persistent, runs on every page), `turnstile-client.js` (loaded only when a challenge is needed), `markdown-enhance.js` and `lore-tooltip.js` live here. The shell and reading-page behaviour moved here from inline blocks: `theme-init.js` (blocking pre-paint theme/lang), `site-shell.js` (i18n, nav, theme buttons, background video, `/posts` tabs), `home-bootstrap.js` (swup-reloaded dashboard bootstrap), `toc.js`, `reading-progress.js` and `status-panel.js`.
- `public/icons/fluent/*.svg` — vendored icon assets referenced through `--fluent-icon-url`; see `scripts/vendor-fluent-icons.mjs`.

Build output goes to `dist/client` and `dist/server` (ignored).
